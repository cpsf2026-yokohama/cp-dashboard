# メンター承認フロー

## 目的

管理画面から行ったスケジュール、動画の削除、バナーの変更と、管理画面・サイト端末から送られる共有設定の変更は申請として保存し、メンターが承認した後に本番データへ反映する。動画アップロードはライブラリへの登録のみなので即時反映する。申請時点では公開中のD1データやR2オブジェクトを変更しない。

## ロール

| ロール | 権限 |
| --- | --- |
| admin | 既存の管理機能。対象変更を申請できるが、申請は即時反映されない |
| producer / operator | 既存の担当機能の範囲で変更を申請 |
| mentor | adminの管理権限に加え、`/mentor` で他のユーザーの申請を承認・却下 |

`/admin` のユーザー管理で「メンター（管理者＋承認）」を割り当てる。申請者本人は承認できない。自分の保留中申請は「取り消す」で削除でき、アカウントIDまたは登録メールアドレスで本人確認する。他の申請は却下できる。

## 承認対象

- 共有設定の値と端末への反映対象
- 再生スケジュールの追加・削除
- 動画の削除（アップロードは承認不要）
- 横型・縦型バナーの追加・削除

ユーザー登録・ロール変更は管理者権限の操作として即時処理する。Cloudflare Accessの許可リストは別途管理する。

## 決裁画面に表示する内容

申請一覧では申請者と申請日時を示し、変更内容をカード内に展開した状態で表示する。共有設定では保存された変更前・変更後の値と端末への反映対象の変更を示す。予定の追加・削除では動画名と日時を示す。動画削除では動画名を示す。バナー変更では現行画像と申請画像を並べ、削除では変更後を「画像なし」と表示する。画像が取得できない場合は空欄にせず、その画像を読み込めなかったことを表示する。

共有設定の配列差分は件数だけでなく、配列の全要素を表示する。申請が不正な形式、未対応項目のみ、または変更前後に差がない場合は承認申請として登録しない。過去の申請で比較情報が不足する場合は「変更前不明」として扱い、現在との差分がないと断定しない。

申請一覧取得に失敗した場合はエラーだけを表示し、「承認待ちの申請はありません」と誤表示しない。バナー画像の取得失敗も、対象画像ごとに明示する。

承認対象のバナー画像はR2の`pending/`領域に置き、メンター画面で現在画像と申請画像を並べて確認できる。申請中画像はメンター認証付きのプレビューAPIで配信する。承認後に公開キーへコピーして保留ファイルを削除し、却下・申請取り消し時も保留ファイルを削除する。申請とレビューの状態はD1の`change_requests`に記録する。共有設定は申請時点の変更前・変更後を保存する。過去形式の保留申請は保存済みの値がないため、現在設定との比較を試み、差分を確認できない場合は申請された値を「変更前不明 → 申請値」として表示する。

## 運用

1. 管理者または担当者が`/admin`で変更する。
2. 画面に「メンターの承認待ち」と表示される。対象の本番データはこの時点で変わらない。
3. メンターが`/mentor`を開き、内容を確認して承認または却下する。申請者本人の保留中申請には取り消し操作を表示する。
4. 承認後、設定・予定・動画削除・バナーが反映される。動画アップロードは完了後すぐライブラリに表示される。設定は端末が次の取得時に読み込む。

承認・却下・申請一覧・保留画像プレビューAPIはCloudflare Access認証を要求し、メンター以外には許可しない。管理者権限だけではレビューできない。申請者自身の承認はユーザーIDと正規化したメールアドレスの両方で拒否する。申請取り消しは申請者本人の保留中申請だけに限り、レビュー処理中の申請は取り消せない。

レビュー状態は`pending`から条件付きで`processing`へ移し、成功時に`approved`または`rejected`へ進める。処理失敗を捕捉できた場合は`pending`に戻す。再実行に備え、同じ申請IDで予定を重複作成しない。バナー画像を公開した後に保留画像がなくても、公開画像の申請IDが一致すれば完了済みとして扱う。動画削除はR2オブジェクトを削除してからD1メタデータを削除し、R2側の失敗で動画レコードだけが先に消える状態を避ける。既に動画メタデータが消えている同じ削除申請は再実行可能な完了済み操作として扱う。D1とR2をまたぐ処理は単一トランザクションではない。Workerが`processing`中に強制終了した場合は状態が残る可能性があり、実データを確認してから運用者が復旧する必要がある。
