# メンター承認フロー

## 目的

管理画面から行ったスケジュール、動画、バナーの変更と、管理画面・サイト端末から送られる共有設定の変更は申請として保存し、メンターが承認した後に本番データへ反映する。申請時点では公開中のD1データやR2オブジェクトを変更しない。

## ロール

| ロール | 権限 |
| --- | --- |
| admin | 既存の管理機能。対象変更を申請できるが、申請は即時反映されない |
| producer / operator | 既存の担当機能の範囲で変更を申請 |
| mentor | adminの管理権限に加え、`/mentor` で他のユーザーの申請を承認・却下 |

`/admin` のユーザー管理で「メンター（管理者＋承認）」を割り当てる。申請者と同じメンターは自分の申請を承認できないが、却下はできる。

## 承認対象

- 共有設定の値と端末への反映対象
- 再生スケジュールの追加・削除
- 動画の追加・削除
- 横型・縦型バナーの追加・削除

ユーザー登録・ロール変更は管理者権限の操作として即時処理する。Cloudflare Accessの許可リストは別途管理する。

動画・バナーのファイルはR2の`pending/`領域に置き、承認後に公開キーへコピーして保留ファイルを削除する。却下時も保留ファイルを削除する。申請とレビューの状態はD1の`change_requests`に記録する。

## 運用

1. 管理者または担当者が`/admin`で変更する。
2. 画面に「メンターの承認待ち」と表示される。対象の本番データはこの時点で変わらない。
3. メンターが`/mentor`を開き、内容を確認して承認または却下する。
4. 承認後、設定・予定・動画・バナーが反映される。設定は端末が次の取得時に読み込む。

## データベース変更

`cloudflare/video-api/migrations/0006_mentor_change_approval.sql` は申請テーブルを追加し、既存ユーザー表のロール制約を拡張する。`0007_claim_change_requests.sql` はレビュー中の二重処理を防ぐ`processing`状態を追加する。リリース時は両migrationを本番D1に適用してからWorkerとPagesを公開する。
