# メンター承認フロー 検査レポート

検査日: 2026-10-19（日本時間）

## 結果

ブラウザーで本番の`/mentor/`とレビューAPIを確認し、メンター権限を持たない現在のブラウザー利用者は申請一覧を取得できず、架空IDへの承認・却下要求も拒否されることを確認した。権限境界と申請処理の回帰テストは37件すべて成功した。

検査中に次の問題を見つけて修正した。ローカル確認済みの変更はGitHubへ反映するが、Worker本番デプロイは別途必要。

1. 共有設定の予定配列を決裁画面で140文字に切り詰めていた。差分配列とオブジェクト全体を表示するよう変更。
2. ユーザーIDが異なっても同一メールアドレスなら自己承認できる可能性があった。承認時にIDと空白・大文字小文字を正規化したメールの両方で自己申請を拒否するよう変更。
3. Accessメールアドレスに複数の大小文字違いのユーザー行が一致する場合、最初のDB行を採用していた。曖昧な一致を認証失敗として扱うよう変更。
4. R2の削除が失敗すると、動画のD1レコードを先に削除して申請が再試行不能になる順序だった。R2を先に削除する順序にし、失敗時はメタデータを残して申請を保留に戻す回帰テストを追加。
5. 未対応の共有設定キー、不正な値、変更のない設定を申請でき、決裁画面に実際の変更が示されない場合があった。未対応・型不正・差分なしの設定申請を登録前に拒否するよう変更。
6. `/mentor/`の申請取得が403になると、エラーに加えて「承認待ちの申請はありません」も表示されていた。取得エラー時は空一覧表示を抑止し、古い申請も一覧から外すよう変更。
7. バナー画像の取得に失敗すると比較枠が空白になっていた。どちらの画像を読み込めなかったか明示する表示を追加。
8. Workerが外部データを反映した後に終了した場合の再試行で、予定の重複や保留画像消失による承認不能が起き得た。同一申請の予定作成とバナー公開を冪等にし、動画削除も既に完了した状態を再試行可能にした。
9. `mentor` にユーザーのロール変更権限まで付与され、本人を `admin` に降格した後も自分を `mentor` に戻せる認可不備があった。ユーザー登録・ロール変更はWorkerで`admin`のみに制限し、本人による`mentor`への昇格も拒否する。管理画面のロール操作も`admin`に限定した。

## 変更ケースの確認

| ケース | 検査内容 | 結果 |
| --- | --- | --- |
| 共有設定 | 変更前後、サイト反映ポリシー、未対応キー、不正値、変更なし | 承認適用・差分テストあり。不正・変更なしは拒否するテストを追加 |
| スケジュール追加 | 申請段階で未反映、メンター承認後の作成、同じ申請の再試行 | 申請・承認後の作成と重複作成防止をテスト |
| スケジュール削除 | 承認後の削除 | 承認後に対象IDを削除するテストを追加 |
| 動画削除 | 担当者制限、承認処理、R2削除失敗時の再試行 | 申請権限、R2失敗から保留に戻ること、成功時の削除順をテスト |
| 動画アップロード | 承認不要で登録し、申請レコードを作らない | 直接アップロードのテストを追加 |
| バナー画像変更 | 保留画像のプレビュー、公開先へのコピー、公開後の再試行 | メンター限定プレビュー、申請ID付きコピー、ステージ画像消失後の再試行をテスト |
| バナー削除 | 承認後に指定方向の公開画像を削除 | 横・縦のキー処理を含む縦型削除をテスト |
| 自分の申請 | 取り消し、別ID・同一メールでの自己承認 | 取り消し可能、自己承認は409で拒否するテスト |
| 二重処理 | `pending`から`processing`への条件付きclaim | 既存の状態claimテストと処理コードを確認 |

## 権限検査

- `GET /api/change-requests`、保留バナープレビュー、承認、却下はCloudflare Access認証を必須とする。
- レビュー操作は`mentor`ロールだけに許可する。`admin`、`producer`、`operator`は拒否されることをロールマトリクステストで確認。
- `/mentor/`を開いた本番ブラウザーでは「メンター権限が必要です」と表示された。
- 同ブラウザーのセッションで申請一覧取得はHTTP 403。架空IDへの承認・却下POSTもHTTP 403、応答は`{"error":"Insufficient permissions"}`。実在の申請IDを使わず、データ変更は発生していない。
- Access認証が大文字小文字違いの複数ユーザーに一致する場合は、ロールを任意に選ばず拒否する回帰テストを追加。
- 申請者本人の取り消しはユーザーIDまたは正規化メールで確認し、他人の申請は削除できない設計を確認。

## 確認範囲と残る注意点

- 現在のブラウザー利用者はメンター権限がないため、実際の保留申請カードをメンター画面で開いて視覚確認することはできなかった。申請種別ごとの適用はWorkerテストで確認し、決裁カードの表示ロジックはソース上で確認した。
- `D1`と`R2`をまたぐ処理は一つのトランザクションではない。処理中にWorkerが強制終了すると`processing`が残る可能性がある。復旧は状態とD1/R2実データを照合して行う必要がある。
- 本番ブラウザーでの拒否確認は現在デプロイ済みコードの挙動。今回の追加修正は未デプロイなので、本番への反映後に同じブラウザー確認を再実施する必要がある。
